## Why complete evidence needs another delivery route

A read-only measurement of the complete historical R10 attempt found 20,480 files
and 790 directories, 625,330,574 logical bytes. PAX tar/gzip at level 6 produced
518,090,004 bytes; the complete member index added 8,789,801 bytes. The combined
526,879,805 bytes already exceeded 500,000,000 bytes before a new candidate tree
or successful production archive. This is a measured historical baseline, not
an estimate of a new run's exact size and not a new native pass.

The original `evidence_pack.py` is unchanged: SHA256
`ee493ee09002132ae47ebfe97b061f17ed6a4c6e1bb1505a944a54c27cd7980a`.
Its original maximum Actions package cap remains 500,000,000 bytes, with the
root choosing a current included-storage cap no larger than that maximum.
Only `Candidate/.git` may be excluded. Derived data, raw xcresults, screenshots,
videos, raw host payloads, empty directories, link metadata, command originals,
source and the unchanged caller verdict must all remain present.

The packer verifies the full archive and then rejects an over-cap total while
retaining its completed outputs. `overflow_evidence.py` catches only that exact
final size rejection. It independently reopens every original and output,
verifies the complete index against actual roots, checks all tar member bytes,
modes, owners, nanosecond times and links, reads gzip through its CRC trailer,
and confirms originals and outputs did not change. Every other packer failure
remains a failure. The rejection is retained in the route receipt; it is never
relabelled an Actions package pass.

A within-cap package uses the original Actions artifact route. An over-cap
package may use only the separately root-bound draft-asset route below. Neither
route may omit or split originals to fit a limit.

The runtime never creates, updates, publishes or deletes a release or tag.
Root creation must be an actual supported authenticated operation; no new
credential, default-branch edit or permission bypass is included. If existing
auth cannot create and read the exact tag/draft, root binding remains blocked.
A create-release API call can require Workflows-write permission when the target
differs from the default branch's workflows; an Actions `GITHUB_TOKEN` cannot
receive that permission. Precreating the draft with proper root authority keeps
that operation outside the runtime asset-upload path.

The root binds actual release ID, author ID/login, creation time, full exact
body/title, source tag target, empty initial asset set, creation receipt hash,
free-route review receipt hash and the full immutable policy. The root review
must bind the same object and all control files.

Before any native work, a scoped job token reads the exact draft, tag and asset
list. A fixed per-candidate reservation filename must be absent. One POST uploads
a small claim containing the actual workflow commit, run ID, attempt 1, source,
root-review digest and draft identity. Its returned ID, uploaded state, length
and SHA256 must match, and its actual downloaded bytes must be identical. The
only asset must then be that exact claim, and the draft/tag are rechecked.
A duplicate filename, uncertain response, corrupt read-back or reused directory
fails without retry or deletion. Native entry requires the complete verified
reservation proof. Reservation success never means native or full-evidence
success. A claim remains even if the eventual evidence fits Actions, preventing
reuse of the same draft by another run.

The workflow requests job-scoped `contents: write` only for this reviewed asset
operation. The token is supplied only to reservation and delivery steps, never
to the native driver or collector. Checkout does not persist credentials. No
runtime endpoint for release/tag creation, modification or deletion exists.

## Complete draft delivery and exact limits

| Asset | Reviewed maximum bytes |
| --- | ---: |
| Complete original `evidence.tar.gz` | 2,000,000,000 |
| Complete member index | 40,000,000 |
| Unchanged caller verdict | 16,384 |
| Delivery receipt | 1,000,000 |
| Reservation claim | 16,384 |

Every individual bound is below GitHub's documented 2 GiB release-asset limit.
The maximum five assets total 2,041,032,768 bytes. No extra asset is accepted.
If any complete asset exceeds its bound, all local originals remain intact and
delivery fails. The native or evidence limits are not expanded automatically.

For actual overflow, unique asset names include the fixed candidate nonce and
actual run, attempt and workflow commit. Each of the archive, index and verdict
gets one POST. Only a 201 response with the exact ID/name/uploaded state/length/
SHA256 is accepted. Each asset is then downloaded and hashed. The three downloaded
originals undergo the full index/tar/link/metadata/gzip CRC verification again
against unchanged source roots. The existing claim and exact uploaded assets
must be the complete remote asset set; the draft and source tag must still match.

A fourth payload asset records the three asset receipts, exact native verdict,
root/run/source context, verification and original nonsecret API responses. It
is itself uploaded and downloaded once. The final gate requires this read-back,
exactly five assets including the reservation, and the unchanged draft/tag.
Because a receipt cannot contain its own future upload response, the final
receipt explicitly labels its own upload pending; the terminal workflow log
contains the actual receipt-upload/read-back outcome and the complete original
transaction ledger. Root must retain that log with the independent downloads.
No native evidence is excluded by this self-reference boundary.

Authenticated requests never follow redirects. An asset download's 302 location
is accepted only for the explicit HTTPS GitHub asset CDN hosts, then fetched
using a new request without Authorization or cookies. Tokens, request headers
and signed URL query strings are not logged. The uploader accepts only the
computed `uploads.github.com` URL for the exact bound repository and release.
Neither duplicate/partial assets nor failed starters are deleted or retried.

The final acceptance gate still requires successful file inspection, reservation,
all native checks, unsigned archive and complete evidence collection. A failed
native verdict remains false after successful asset delivery. Normal Actions
and draft overflow are mutually exclusive routes, and draft acceptance also
requires the exact collected archive hash/length. Signing, original-pixel review,
independent root download, Grok delivery and store submission remain separate.

## Free-use and visibility basis

The official Releases documentation permits up to 1,000 assets, each under 2 GiB,
and describes no aggregate release-storage or bandwidth limit. GitHub's plans
page includes full public-repository features on Free. Actions/Packages shared
artifact storage is described separately in their billing documentation. The
proposal's zero-extra-spend conclusion for standard public-repository Releases
is an **inference from those documented feature and billing boundaries**, not a
new measured account billing statement or a purchase authorization. Root must
review that basis and current account policy before binding. No paid plan,
package registry, LFS purchase or billable-storage increase is requested.
The normal Actions route still requires an explicit root allowance plus reserve
under the existing zero-dollar hard stop. The previous v3 root binding used a
20,000,000-byte cap and 21,000,000-byte local per-attempt allowance; those were
not a provider reservation or an exact live storage balance. V4 remains unbound
until root reviews the current account evidence and allowance. Quota refusal
fails delivery and never enables paid fallback or evidence deletion.

The draft remains unpublished and is available through authorized repository
access. It is not a durable secret vault: authorized writers can change drafts.
Identity is therefore checked before reservation and again throughout delivery.
Only screened source and synthetic QA evidence belong in this package. The
token is excluded from native subprocess environments and evidence ledgers.
